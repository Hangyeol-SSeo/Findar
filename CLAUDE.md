## Architecture

Findar scrapes the KOFIA (금융투자협회) member-firm job board, AI-summarizes and matches postings against the user's resume, does on-demand deep research on the hiring company, and drafts application content. Persistence is **SQLite via `better-sqlite3`** (`lib/db.ts`, file at `data/findar.db`) — there is no file-based JSON cache anymore (an older `lib/cache.ts` was fully replaced; `lib/db.ts` still has a one-time `migrateLegacyCache()` importer for the legacy `.cache/jobs.json` shape, but that file doesn't exist in a fresh checkout).

### Job pipeline: `app/api/jobs/route.ts` (GET `/api/jobs`)

Always streams **Server-Sent Events** (`data: {...}\n\n` frames) — there is no non-streaming JSON response mode. Query params: `pages` (default `CRAWL_PAGES`, clamped to 50 — not 15), `match` (`"false"` disables matching).

1. Sends `{type:"cached", jobs}` immediately from `getActiveJobs()` so the UI isn't blank while crawling starts.
2. Resolves the resume profile (`lib/profile.ts` `ensureProfile()`) unless matching is disabled; emits `profile-ready`.
3. **List crawl** (`lib/crawler.ts` `fetchListPage`) — paginates `kofia.or.kr/brd/m_96/list.do`, emits `crawl-list`.
4. **Detail crawl** (`fetchDetailPage`) — only for seqs not already summarized (`getExistingSeqs`); emits `crawl-detail`.
5. **AI summarization** (`lib/summarizer.ts`, batched via `SUMMARIZE_BATCH_SIZE`) + **matching** (`lib/matcher.ts`, batched) per chunk, persisted via `upsertJob`/`updateJobMatch`. Emits `summarize-progress` (job included) then, if profile changed, a `rematch` phase + `rematch-progress` for existing jobs whose `matchProfileHash` is stale.
6. Emits `done` with `getActiveJobs()` (the authoritative final list) + `newCount`/`hasProfile`.

A 1000 ms `sleep` separates every outbound KOFIA HTTP request (list and detail pages) — preserve this. Summarizer/matcher prompts truncate `job.content` to **3000 chars** (not 2000).

### Database: `lib/db.ts`

Tables, keyed off the crawler's `seq` (job posting id) or a normalized company name:

- **`jobs`** — one row per posting. `categories` is populated by `categorizePositions()` (`lib/position-categories.ts`) inside `upsertJob()` itself, so every caller (route, legacy migration) gets it for free; a one-time `backfillCategories()` fixes rows written before this existed. `getActiveJobs()`/`getJobsNeedingMatch()` both `LEFT JOIN applications` (see below) — **never query `jobs` alone when the result reaches the client**, or `applicationStatus` silently reverts to `미지원`. Also carries two boolean-ish flags set only via user action, never by the crawler: `hidden` (excluded from `getActiveJobs()` entirely — `GET`/`POST /api/jobs/hide`, `{seqs}` / `{seq, hidden}`) and `bookmarked` (**not** excluded — rides along on every job object like `applicationStatus` does, so "찜한 공고만 보기" is a client-side filter over the normal list, not a separate server-side view — `POST /api/jobs/bookmark`, `{seq, bookmarked}`).
- **`applications`** — per-job application status (`lib/application-status.ts`: 미지원/검토중/작성중/제출완료/서류합격/면접/불합격/최종합격), `notes`, an append-only `history` JSON array, `submittedAt` (set once, on first transition into `제출완료`, never overwritten). Written via `upsertApplicationStatus()`, exposed as `POST /api/applications` (`{seq, status, notes?}`, same shape as the pre-existing `/api/jobs/hide`). `getActiveJobs()` drops postings past their deadline, so applications in `TRACKED_APPLICATION_STATUSES` (검토중/작성중/제출완료/서류합격/면접/불합격/최종합격) are served separately by `getTrackedApplicationJobs()` → `GET /api/applications/tracked` with **no deadline and no `hidden` filter** (plus `submittedAt`/`expired`) — the board's "지원 현황" view reads that, not the active list. Deliberately a separate table from `jobs` — like `hidden`, this must survive a recrawl's `upsertJob` without being clobbered.
- **`sheet_sync_pending`** — retry queue for the Google Sheet sync below (seq only; the payload is rebuilt from current state at send time).
- **`companies`** / **`company_sections`** — company research cache, see below.
- **`application_drafts`** — one cached AI-drafted application per `seq` (see below).
- **`essay_events`** — append-only essay writing/revision log (see "Essay writing log" below).

### Company research: `lib/dart.ts` + `lib/company-research.ts`

KOFIA postings carry **no company ID**, only a free-text `company` string, and no financial data at all. `lib/company-normalize.ts`'s `normalizeCompanyName()` (strips `(주)`/`㈜`/`주식회사`/whitespace) is the *only* identity key — always use it, never re-derive normalization elsewhere.

- **`lib/dart.ts`** — OpenDART (전자공시시스템) client, gated on `process.env.DART_API_KEY` (`isDartConfigured()`). There is no company-name search API, so `findCorpCode()` downloads the full corp-code list (`corpCode.xml`, unzipped via the system `unzip` binary — not a new npm dep — and parsed with `cheerio`'s `xmlMode`) once, caches it to `data/dart-corpcodes.json` (refreshed every `DART_CORP_CODE_REFRESH_DAYS`), and matches locally (exact, then substring fuzzy). `fetchKeyFinancials()` matches accounts by **`account_id` (IFRS code) first, falling back to exact `account_nm` match** — a real bug was found and fixed here: substring-matching account names picked up `자본과부채총계` (assets total) for a `부채총계` (liabilities) search, because `.includes()` matched the wrong row.
- **`lib/company-research.ts`** — five independent sections (`lib/company-section-types.ts`: `overview`, `culture`, `governance_structure`, `financials`, `news`), each with its own TTL (`COMPANY_SECTION_TTL_DAYS` in `lib/config.ts`) so a "refresh" never re-runs sections that are still fresh. All five are deliberately **deep, not quick summaries** — first shipped as a 4-turn `WebSearch`-only Haiku call asking for "3-5문장", which the user correctly called out as too shallow to avoid looking uninformed when applying. The default research model is `claude-sonnet-5-5`, configurable in the settings page, `allowedTools: ["WebSearch", "WebFetch"]` (must actually open and read pages, not just skim search snippets), `maxTurns: 25` for every section including the DART-grounded ones (`financials`/`governance_structure` start from real DART numbers/exec data via `runGroundedResearchSection` but still search+fetch to add industry context and interpretation — a first attempt at `maxTurns: 15` measurably hit the turn ceiling and failed on `governance_structure` in testing, so don't set it lower again without re-verifying live). Prompts explicitly ask for 1000+ characters, multiple paragraphs, ≥3 real sources actually fetched, and — for `overview` — a "why is this company hiring right now" analysis tying the role to the company's current situation. These calls intentionally **bypass `getAIModelOptions()`/FreeRide** and always hit Anthropic directly — WebSearch/WebFetch are native Anthropic server tools a local FreeRide gateway likely can't proxy. Sources are extracted from the model's own `[title](url)` markdown links in its answer, not from parsing tool-call internals. Research is **lazy and manual-only** — there is no config flag or background job that researches all KOFIA members automatically; a company is only looked up when its "회사 리서치" tab is opened and the user clicks the refresh button, and only stale/missing sections are (re)run then. A single deep section now realistically takes minutes (real WebFetch calls are slow) and costs meaningfully more than the old shallow version — an accepted, explicit tradeoff for this feature, not true of the rest of the app's AI calls.
- API: `GET /api/companies/[normalizedName]` (pure cache read, no AI cost, upserts the `companies` row from `?displayName=`) and `POST /api/companies/[normalizedName]/research` (SSE, same `data: ...\n\n` framing as the jobs route; body `{displayName, sections?}`).

### Profile & matching: `lib/profile.ts` + `lib/matcher.ts`

- Resume PDFs are **uploaded from the web** (`/settings` → 이력서 tab, `components/ResumeUploadForm.tsx`) via `GET`/`POST`(multipart `files`)/`DELETE ?name=` `/api/profile/resume`, and stored in `data/resume/` (`lib/resume-files.ts` — `%PDF-` magic check, sanitized basename, 20MB/10 files, same name = replace). `POST /api/profile/resume/analyze` runs `ensureProfile()` immediately instead of waiting for the next crawl. The old repo-root `resume/` dir is legacy: `lib/profile.ts` moves its PDFs into `data/resume/` once at module load and, if content is unchanged, rewrites the cached `sourcesHash` and every job's `matchProfileHash` (`remapMatchProfileHash`) so the move doesn't trigger a re-extraction or full rematch. `ensureProfile()` extracts a structured `Profile` agentically (`allowedTools: ["Read"]`, the SDK reads the PDFs itself) and caches it to `data/profile.json`, keyed by `hashResumeSources()` (file **name + content** hash — re-uploading an identical file costs nothing). Concurrent extractions of the same hash share one in-flight promise. This call **always uses the raw Anthropic API**, never FreeRide, since resumes are PII.
- `Profile.transferableStrengths` (extracted from the resume) and `Profile.careerGoals` (user-authored, **not** inferable from a resume) both feed the matcher prompt so a CS/dev-heavy resume doesn't implicitly get scored as IT-only fit. `careerGoals` lives in a separate file, `data/profile-overrides.json` (`readCareerGoals`/`writeCareerGoals`), edited at `/settings` (`GET`/`PUT /api/profile/overrides`) — kept independent of the resume-hash cache so editing it never triggers (or requires) a resume re-extraction. `getCachedProfile()`/`ensureProfile()` both merge the override in fresh on every call via `withCareerGoals()`.
- `lib/matcher.ts` has **no category gate** — it already scores every job regardless of category; `positionType`/category bias, if any, comes from the profile's own material, not a code-level restriction.

### Resume tailoring (이력 구성): `lib/resume-tailoring.ts` + `lib/resume-inventory.ts` + `lib/resume-tailoring-contract.ts`

Per-job evaluation of *what to put on the resume*: every resume/applicant-profile item gets a decision — `강조`/`유지`/`축소`/`제외`/`숨김 검토` (plus `판단 보류` for items the model skipped; `normalizeTailoring()` never drops an item). Shown in the job side panel's **이력 구성** tab (`components/ResumeTailoringPanel.tsx`).
- `Profile` is a matching summary and drops small items (old activities, minor certs, hobbies) — exactly the items this feature judges — so `ensureResumeInventory()` separately extracts a **complete item-level list** from the PDFs (`data/resume-inventory.json`, same `hashResumeSources` key, lazy: only on first use, never in the crawl pipeline). `buildApplicantItems()` adds the user-authored `ApplicantProfile` entries (`a.*` ids) deterministically; required form fields (birthdate, gender, contact) are excluded, optional ones (religion, hobbies) included.
- One tool-less Sonnet call per evaluation, direct Anthropic (full resume content = PII). The prompt's honesty rules are the point of the feature: it may recommend *omitting* or *refocusing* but never altering facts, and must warn (`omissionRisk`) instead of recommending omission when leaving an item out could count as 경력 누락/허위 기재.
- `POST /api/applications/[seq]/tailoring` runs as an `ApplicationTask` of kind `"tailoring"` (same task store/polling as essay writing — `ApplicationDraftPanel` filters these out); `GET` is a pure cache read from the `resume_tailoring` table with a `stale` flag (hash of resume files + applicant `updatedAt` + `careerGoals`).

### Application drafting: `lib/application-draft.ts` + `lib/application-method.ts` + `lib/applicant-profile.ts`

- **`lib/applicant-profile.ts`** — a large, 100% user-authored (no AI) structured record: name/English name/gender/birthdate/photo(data URL)/nationality/address/email/phone/disability/veteran/military status, plus repeatable arrays for education, research, language tests, certifications, awards, activities, work experience, and projects. Filled at `/settings` (`components/ApplicantProfileForm.tsx`) via `GET`/`PUT /api/profile/applicant`, stored in `data/applicant-profile.json`. This exists because the AI-derived `Profile` (from resume PDFs) simply doesn't contain fields like email/birthdate/school name/military service — real Korean application forms (NCS-style especially) ask for all of them, in granular repeated sections. **If you (Claude) are asked to fill out a real application form for the user, `GET /api/profile/applicant` is the authoritative source for this data — use it verbatim, don't re-derive it from the resume.**
- `generateApplicationDraft(seq)` builds personal-info fields + essay-question answers from the job + cached `Profile` + any cached `company_sections`. If `isApplicantProfileFilled()`, `personalFields` is **not** AI-generated at all — `buildPersonalFieldsFromApplicantProfile()` deterministically flattens the structured applicant profile into `{label, value}` pairs (one per scalar field, one per array entry), and the AI call's JSON schema skips asking for `personalFields` entirely to save tokens. Only `essayAnswers` (and, when unfilled, `personalFields` as a same-shape fallback) come from the model. `stripForbiddenFields()` hard-deletes anything matching 주민등록번호/계좌번호/비밀번호/etc. from either path, even if user-entered. Cached in `application_drafts`; `GET`/`POST`/`PUT /api/applications/[seq]/draft`.
- `detectSubmissionMethod()` (`lib/application-method.ts`) is a **pure, AI-free heuristic** run fresh on every draft `GET` (cheap enough not to cache): scans `job.attachments` filenames for an application-template pattern (입사지원서/지원서/...) vs. a consent-form pattern (개인정보...동의서), and `job.rawContent` for a submission email. Real crawled data showed **KOFIA postings are dominated by email+attachment submission**, not web ATS forms — check both signals, don't assume `siteUrl` means a fillable web form.
- **Essay/자소서 questions are unknowable up front.** KOFIA postings almost always just say "자유 양식" for the 자기소개서 — the real, exact question wording (if any) only exists on the external form or inside the attached template, neither of which this app parses. So `generateApplicationDraft()` always drafts the full `COMMON_ESSAY_QUESTIONS` set (`lib/essay-questions.ts`: 지원동기/성장과정/성격장단점/입사후포부/문제해결경험/갈등대처경험/본인소개/직무역량) **plus** one `COMBINED_ESSAY_LABEL` answer (a single flowing 1000+자 essay covering the same themes at once, for forms that want one big free-text box instead of separate questions) — both shapes are common in the wild. For the (frequent) case where the real form's wording doesn't match any of these, `generateCustomEssayAnswer(seq, question)` (`POST /api/applications/[seq]/draft/question`) takes the **exact pasted question text** and drafts one answer for it, appending it into the same cached `ApplicationDraft` (creating a minimal draft first if `generateApplicationDraft` was never run) — this is the path a live Claude-in-Chrome fill session should prefer once it sees the real form's actual questions.
- **`lib/essay-bank.ts`** is the "발전 가능한" feedback loop the user asked for: a growing corpus of the user's own past 자소서 writing, stored in `data/essay-bank.json`. Two ways entries get in: (1) the user uploads past 자소서 **and 면접 대본** at `/settings` → 과거 자소서·면접 (`components/EssaySourceUploadForm.tsx`, `GET`/`POST`(multipart `kind`+`files`, or JSON `{kind,title,text}` paste)/`DELETE ?kind=&name=` `/api/essay-sources`). `lib/essay-sources.ts` stores them under `data/essay-sources/{cover-letters,interviews}/` (PDF magic-checked; TXT/MD as-is; DOCX/HWPX converted to `.txt` at upload via system `unzip` — Read can't open them; HWP rejected with a "save as PDF/HWPX" message; the legacy repo-root `cover-letters/` dir is moved in once). `ensureEssayBank()` then extracts **per file**, cached by file name+content hash and model in `bank.files`, so only new/changed files cost a call: PDFs via `allowedTools: ["Read"]`, text inline with no tools; `{company, question, answer, context}` with answers **verbatim** (for text sources `verbatim` is checked in code and the UI warns when it's false); entries carry `kind`/`sourceFile`, and a deleted file's entries are dropped on the next run. A failed file is not retried automatically (writing calls `ensureEssayBank()` every time — that would re-bill on each draft); only "실패한 파일 다시 분석" (`retryFailed`) retries. `styleNotes`/`recurringThemes` come from one tool-less call over the extracted answers, only when the set of analyzed files changes. `POST /api/essay-sources/analyze` runs it in the background; the settings UI polls `progress`. All bank writes go through `updateBank()` (re-read + atomic rename) because a run takes minutes while edit signals/saved answers keep landing; (2) `appendEssayEntry()` (`POST /api/essay-bank`, wired to each essay answer's "자료로 저장" button in `ApplicationDraftPanel`) lets the user save an answer they've actually finalized/edited in the app — these `source: "saved"` entries are never overwritten by re-extraction. `summarizeEssayBankForPrompt()` feeds the most recent entries + style notes into every draft/custom-question prompt so future drafts reuse real episodes and match the user's own voice instead of generic AI phrasing — and each generation potentially adds material back into the bank, so the corpus (and draft quality) is meant to compound over time.
- **`lib/narrative-profile.ts`** (+ `lib/narrative-questions.ts`) fills the gap none of the above cover: the user's actual values, the real reasons behind past choices, and where they want to go — not skills or work history. It exists specifically for jobs whose domain is **distant from the resume's career history**, where `Profile`/`ApplicantProfile`/essay-bank alone push the model toward strained skill-stretching ("data pipeline experience → applicable to risk analysis") instead of a genuine "why this role" narrative. Stored in `data/narrative-profile.json`, same JSON-file convention as `applicant-profile.ts` (no SQLite table), **100% user-authored, no AI extraction** — this data can't be inferred from a resume, and having AI invent it would be exactly the "AI did all the thinking" impression the user is trying to avoid. Two parts: `core` (4 fixed, rarely-changing fields — `coreValues`/`workCriteria`/`futureDirection`/`opennessToNewFields`, the last one being the most direct bridging material, always included in full) and `episodes` (an essay-bank-style growing list, seeded from `NARRATIVE_SEED_QUESTIONS`' 8 reflective questions but extensible via "경험 추가"; each splits `situation` (fact) from `reasoning` (the judgment criteria actually used at the time) so the model can quote `reasoning` as the real motive instead of blending fact and motive). `summarizeNarrativeForPrompt()` ranks episodes by tag/keyword overlap with the job but — this is the key design choice — **never returns an empty result when overlap is zero**; it falls back to the most recent episodes instead, because a zero-overlap job is exactly the "distant job" case where this material is needed most ("looks irrelevant → still include it," not "looks irrelevant → omit it"). No programmatic "is this job distant?" heuristic was added (a keyword-table version was considered and rejected as another brittle layer); instead `buildDraftContext`/`backgroundPromptBlock` in `lib/application-draft.ts` always includes a static instruction telling the model to lean on this material instead of skill-stretching whenever the job looks distant from the resume — the model already has both texts in context and can judge distance itself. Settings UI at `components/NarrativeProfileForm.tsx`, `GET`/`PUT`/`POST /api/profile/narrative` + `PUT`/`DELETE /api/profile/narrative/[id]`.
- **Essay revision (첨삭): `lib/essay-revision.ts` + `components/EssayRevisionTools.tsx`.** Distinct from regenerating ("새로 쓰기", the full plan→materials→write→edit pipeline, 4–6 Sonnet calls): 첨삭 starts from the *current* text and makes **one** Sonnet call (one retry only on format/rule failure), sending only cited `company.*`/`past.*` sources plus the current text as a `user.answer` source instead of the full 150k bundle. Two modes, both run as an `ApplicationTask` of kind `"revision"` (mutually exclusive with `"writing"` per seq, since both read-modify-write the same draft JSON): **고쳐쓰기** (`reviseEssay`) stores a `pendingRevision` the user accepts/discards after a sentence-level diff (`lib/essay-diff.ts`), and **첨삭 받기** (`reviewEssay`) stores `feedback` with phrase-level `suggestions` whose `original` must be an exact substring of the text — applying one is a plain string replace with no AI call. All validation is deterministic (honorifics, char limit, forbidden names, unsupported numbers); invalid suggestions are dropped, not retried. The opinion-type fact-audit call is intentionally skipped for revisions (agreed cost tradeoff). Every text change appends to `EssayAnswer.versions` (last entry = current text, capped at `MAX_ESSAY_VERSIONS`, restorable) — including manual edits saved via `PUT /draft` and regenerations in `persistEssay`. "내 글 가져오기" (`POST /draft/import`) stores a user-written answer (`origin: "imported"`, no AI). Synchronous actions go through `POST /draft/answer-action` with the draft `revision` for conflict detection. Manual edits and accepted/dismissed suggestions are logged as `editSignals` in `data/essay-bank.json`; `summarizeEditPreferences()` feeds recent pairs into every draft/revision prompt so output drifts toward the user's own phrasing — raw examples, no summarization call.
- **Revision needs-info + industry research (업계 사례 조사): `lib/industry-research.ts`.** When a 고쳐쓰기 request needs facts that aren't in the sources, `reviseEssay` stores `revisionNeedsInfo` (questions) instead of failing — the UI offers "answer and retry", "proceed conditionally" (no specific institutions/dates), or industry research. Research runs **only on button press**, as `ApplicationTask` kind `"research"` (same per-seq exclusivity as writing/revision), in two stages so the user steers mid-way: `scopeIndustryResearch` (WebSearch only, ≤3 searches, no page fetches) returns candidate sources + "how should this be structured" questions; the user picks ≤5 sources and writes a direction; `collectIndustryResearch` WebFetches only those URLs and extracts `{fact, quote, date}` findings (URLs not in the picked set are dropped). The user then picks findings and requests a rewrite, which passes them to `reviseEssay` as `research.*` sources. Uses the `industryResearch` model setting and calls Anthropic directly (server tools). Findings' quotes come from the model's own fetch (same trust model as company research), so the UI tells the user to verify via the link. Task completion/failure for revision/research shows a toast, scrolls to and briefly highlights the affected answer, and shows failures inline under that answer (only for tasks observed running in the current mount, so reopening a panel doesn't jump around).
- **Essay writing log (작성 기록): `lib/essay-log.ts` + `lib/essay-log-analysis.ts`.** Every essay action is appended to the SQLite `essay_events` table (append-only — never update or delete rows): 작성 요청/초안/실패, 내 글 가져오기, 직접 수정, 고쳐쓰기 요청→수정본/보완 질문/실패→반영/버림, 첨삭 받기 요청→피드백→제안별 반영/넘김→닫기(손대지 않은 제안 포함), 버전 복원, 업계 조사 각 단계, 자료로 저장. `application_drafts` only holds current state (closed feedback and discarded rewrites vanish there), so this log is the only record of *how* an answer evolved and what the user asked for or rejected. Events carry `actor` (user/ai/system), a `threadId` linking a request to its AI result and the user's accept/discard (stored as `threadId` on `PendingRevision`/`EssayFeedback`/`RevisionNeedsInfo`/`IndustryResearch`), full `textBefore`/`textAfter`, and a deterministic `analysis` (`analyzeEssayChange`: sentence-level hunks split per paragraph, each with `zone` 도입/본문/마무리, paragraph number, and tags like 단서 제거/의견형→단정형/축약/문장 분리, plus `inspectEssayStyle` codes resolved/introduced). `summarizeEssayEvents` aggregates requests with outcomes, suggestion stats per category, where/how the user edits by hand, and which style issues the user fixes vs. the AI introduces. Read via `GET /api/essay-log` (`view=summary`, `format=jsonl` export, filters `seq`/`question`/`type`/`threadId`/`since`/`until`/`limit`/`text=0`). No AI calls; logging failures are swallowed so they never block the actual save. On first load it backfills answers that have no events yet from their `versions` and any open feedback/rewrite (marked `detail.backfilled`). **Any new essay action must log an event here.** Covered by `scripts/tests/essay-log.cjs`.
- **Essay style rules: `lib/essay-style.ts`.** `STYLE_RULES` (appended to `WRITING_RULES`, and added to the 첨삭 받기 prompt) targets problems seen in real output: personal experiences grafted one line per claim instead of one coherent paragraph, experiences stretched into analogies for company/industry problems, self-descriptions contradicting the story told, research facts piled in (including ones the essay itself calls "just a reference"), "한 증권사"-style anonymized sources, hedges ("다만") and opinion endings ("생각합니다/봅니다") on every sentence, vague metaphors. `lintEssayStyle()` is a free deterministic check (hedge count, opinion-ending ratio, same final word 3× in a row, anonymized-source phrases, sentences >110 chars): its findings are fed into the generation editor pass and the review prompt (no extra AI call) and appended to `reviewNotes` as "문체 점검: …" for drafts and rewrite proposals. Covered by `scripts/tests/essay-style.cjs`.
- **No Playwright / in-app browser automation.** It was prototyped and removed: real ATS forms (tested live against a greetinghr-hosted form) vary too much site-to-site — inconsistent labels, deeply nested field names, file uploads, consent checkboxes — for a hardcoded field-matcher to be reliable. Instead, `ApplicationDraftPanel` surfaces a copyable prompt (`이 공고 지원 도와줘 (seq=N)`) for the user to hand to a live Claude Code + Claude-in-Chrome session, which reads the real page and fills it with judgment — pulling personal info from `GET /api/profile/applicant` and essay content from the job's draft. Findar's job stops at producing a good draft + submission-method hint; it never automates the actual site, and never has code capable of clicking a submit button.

### AI model settings

`/settings` → **AI 모델** provides a select box for each of the ten AI features. `lib/ai-model-types.ts` owns the feature/model catalog and all model ID constants; `lib/ai-model-settings.ts` reads and validates selections, persists them atomically to ignored `data/ai-model-settings.json`, and resolves the provider at each new operation. Environment values (`USE_FREERIDE`, `FREERIDE_MODEL`, `COMPANY_RESEARCH_MODEL`) supply defaults until a web selection is saved. Saved Sonnet 5 selections resolve to Sonnet 5.5. Only public-job summarization and matching offer FreeRide; resume PDFs, application data, company research, and industry research use Claude. Changing a selection takes effect without a restart; a running operation keeps its original model. Cached research/profile/inventory/tailoring/material results recognize model changes when those features are used or refreshed. New AI features must register in this catalog and call the shared resolver rather than hardcode a model.

### Google Sheet sync: `lib/sheet-sync.ts` + `scripts/google-sheet-sync.gs`

When `POST /api/applications` changes a status, `after()` pushes that application to the user's own 지원 현황 Google Sheet via an Apps Script web app (`scripts/google-sheet-sync.gs`, pasted into the sheet's Apps Script editor and deployed by the user — not an MCP connector, which the app itself can't call). Gated on `FINDAR_SHEET_SYNC_URL` + `FINDAR_SHEET_SYNC_TOKEN`; no-op without them. Only statuses from `제출완료` onward are written (검토중/작성중 are "not applied yet"). The script matches rows by the KOFIA `seq=` in the 링크 column, updates only 단계/결과 on existing rows (other cells only if blank, so manual edits survive), leaves 이력서 버전 blank, and colors 결과 (탈락 `#ff6d01`, 합격 `#4285f4`). Sends are serialized in-process so rapid status changes can't land out of order; failures stay in `sheet_sync_pending` and are retried on the next status change or `GET /api/applications/tracked`.

None are committed (`.env*` is gitignored). ## Conventions specific to this repo

- **Korean UI strings stay in Korean** (titles, badges, status messages, filter labels, prompts).
- Category classification (`lib/position-categories.ts`) has **no fixed whitelist in the AI prompt** — `CATEGORY_RULES` is a client+server-shared keyword-matching table, order-sensitive (first match wins, so more specific categories like 퀀트/WM-PB must precede broad ones like IT/개발). AI-returned `positions` are always free text; categorization happens afterward in code.
- Failure mode for summarization/matching/company-research/drafting is **degraded entries**, never dropped/thrown data: `positionType: "미분류"`/`jdSummary: "요약 실패"` for jobs, `FALLBACK_MATCH` for matches, `status: "failed"|"partial"` rows (with an explanatory `content` string) for company sections — preserve this pattern in any new AI call.
- New mutable per-job user state needs to survive a recrawl's `upsertJob()` without being clobbered. Two ways to do that: its own table (`applications`, `application_drafts`), or a `jobs` column deliberately left OUT of `upsertJobStmt`'s `ON CONFLICT DO UPDATE SET` clause (`hidden`, `bookmarked`) — either is fine, but a new `jobs` column that *is* included in that SET clause will silently reset on every recrawl.
- AI calls that only see *derived* data (summaries, profile fields, public company info) may route through `getAIModelOptions()`/FreeRide, matching `matcher.ts`'s existing precedent; calls touching raw resume PDFs (`lib/profile.ts`) or Anthropic-native server tools like WebSearch (`lib/company-research.ts`) always call the Anthropic API directly.
- Never add code capable of submitting a third-party form or clicking a submit-like control — the whole application-assist feature set is designed to stop one step before that, by construction, not just by prompt instruction.
