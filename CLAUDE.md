## Architecture

Findar scrapes the KOFIA (금융투자협회) member-firm job board, AI-summarizes and matches postings against the user's resume, does on-demand deep research on the hiring company, and drafts application content. Persistence is **SQLite via `better-sqlite3`** (`lib/db.ts`, file at `data/findar.db`) — there is no file-based JSON cache anymore (an older `lib/cache.ts` was fully replaced; `lib/db.ts` still has a one-time `migrateLegacyCache()` importer for the legacy `.cache/jobs.json` shape, but that file doesn't exist in a fresh checkout).

### Job pipeline: `app/api/jobs/route.ts` (GET `/api/jobs`)

Always streams **Server-Sent Events** (`data: {...}\n\n` frames) — there is no non-streaming JSON response mode. Query params: `pages` (default `CRAWL_PAGES`, clamped to 50 — not 15), `match` (`"false"` disables matching).

1. Sends `{type:"cached", jobs}` immediately from `getActiveJobs()` so the UI isn't blank while crawling starts.
2. Resolves the resume profile (`lib/profile.ts` `ensureProfile()`) unless matching is disabled; emits `profile-ready`.
3. **List crawl** (`lib/crawler.ts` `fetchListPage`) — paginates `kofia.or.kr/brd/m_96/list.do`, emits `crawl-list`.
4. **Detail crawl** (`fetchDetailPage`) — only for seqs not already summarized (`getExistingSeqs`); emits `crawl-detail`.
5. **AI summarization** (`lib/summarizer.ts`, batched via `SUMMARIZE_BATCH_SIZE`) + **matching** (`lib/matcher.ts`, batched) per chunk, persisted via `upsertJob`/`updateJobMatch`. Emits `summarize-progress` (job included) then, if profile changed, a `rematch` phase + `rematch-progress` for existing jobs whose `matchProfileHash` is stale.
6. Emits `done` with `getActiveJobs()` (the authoritative final list) + `newCount`/`hasProfile`.

A 1000 ms `sleep` separates every outbound KOFIA HTTP request (list and detail pages) — preserve this. Summarizer/matcher prompts truncate `job.content` to **3000 chars** (not 2000).

### Manually added postings: `lib/manual-jobs.ts` + `lib/manual-job-save.ts`

The KOFIA board misses many postings. Firms that post their 경력 수시 there still run 신입 공채·인턴 only on their own recruiting sites: 메리츠 recruit-meritz.com, NH/KB on recruiter.co.kr, whose data API is robots-disallowed. So the board has **공고 직접 추가** (`components/ManualJobForm.tsx`). The user enters company, title, optional link and deadline, and pastes the body. `POST /api/jobs/manual` (same-origin) stores it in `jobs` with a `manual-…` seq; KOFIA seqs are digits, and the crawler's `upsertJob` never touches these rows. It then runs the same `summarizeJob` + `matchJobBatch` on that one posting. Matching uses the cached profile only.
- **Failures:** a failed summary still saves with `summarizedAt` set, so it shows as "요약 실패"; nothing re-summarizes it later. Re-saving via 공고 수정 (`GET`/`POST` with `seq`) retries.
- **Edits:** an edit that leaves company/title/body unchanged reuses the summary and match without an AI call. A re-summarized edit clears the old score (`clearJobMatch`), so a failed match falls to the next rematch.
- **Deadline and link:** a user deadline overrides the AI one. `siteUrl` holds the posting link.
- **링크에서 본문 읽기:** `POST /api/jobs/manual/read` does one fetch through `fetchPublicPage()`, shared with the research `read_page` tool. It handles public hosts only, never bypasses blocks, and does no AI. Most ATS pages are script-rendered, so this usually says to paste.
- **Code that used to assume numeric KOFIA seqs:** `postingLink()` gives the KOFIA URL or the manual link (or null) for the board footer, research postings and the sheet `link`. `getCompanySiteUrls` skips manual rows (their link isn't a homepage). Company posting queries order by `date`, not `CAST(seq)`. The Apps Script accepts `manual-…` seqs and finds those rows by a `findar:<seq>` note on the link cell, so the user must redeploy it.

**Image-only postings** are common in Korea: the whole body is one tall JPG. The form takes images by file, drag-and-drop or ⌘V paste. 링크 읽기 also returns the page's body images (`contentImages` + `fetchImage` with large limits). When the page has no usable text, it reads them right away.
- **Slicing:** the browser (`sliceImage` in `ManualJobForm`) cuts each image into JPEG slices of at most 1600×2000 that overlap by 60px (`POSTING_IMAGE_LIMITS`), because tall images exceed model image limits.
- **Transcription:** `POST /api/jobs/manual/images` sends up to 20 slices per call. It checks each slice's type from its bytes (`parsePostingImages`). `lib/posting-image-text.ts` transcribes them in one tool-less call, using the **공고 이미지 판독** (`postingImage`) model setting.
- **Result:** the text is appended to the body field for the user to check before saving. Images are never stored.

Covered by `scripts/tests/manual-jobs.cjs`.

### Database: `lib/db.ts`

Tables, keyed off the crawler's `seq` (job posting id) or a normalized company name:

- **`jobs`** — one row per posting. `categories` is populated by `categorizePositions()` (`lib/position-categories.ts`) inside `upsertJob()` itself, so every caller (route, legacy migration) gets it for free; a one-time `backfillCategories()` fixes rows written before this existed. `getActiveJobs()`/`getJobsNeedingMatch()` both `LEFT JOIN applications` (see below) — **never query `jobs` alone when the result reaches the client**, or `applicationStatus` silently reverts to `미지원`. Also carries two boolean-ish flags set only via user action, never by the crawler: `hidden` (excluded from `getActiveJobs()` entirely — `GET`/`POST /api/jobs/hide`, `{seqs}` / `{seq, hidden}`) and `bookmarked` (**not** excluded — rides along on every job object like `applicationStatus` does, so "찜한 공고만 보기" is a client-side filter over the normal list, not a separate server-side view — `POST /api/jobs/bookmark`, `{seq, bookmarked}`).
- **`applications`** — per-job application status (`lib/application-status.ts`: 미지원/검토중/작성중/제출완료/서류합격/면접/불합격/최종합격), `notes`, an append-only `history` JSON array, `submittedAt` (set once, on first transition into `제출완료`, never overwritten). Written via `upsertApplicationStatus()`, exposed as `POST /api/applications` (`{seq, status, notes?}`, same shape as the pre-existing `/api/jobs/hide`). `getActiveJobs()` drops postings past their deadline, so applications in `TRACKED_APPLICATION_STATUSES` (검토중/작성중/제출완료/서류합격/면접/불합격/최종합격) are served separately by `getTrackedApplicationJobs()` → `GET /api/applications/tracked` with **no deadline and no `hidden` filter** (plus `submittedAt`/`expired`) — the board's "지원 현황" view reads that, not the active list. Deliberately a separate table from `jobs` — like `hidden`, this must survive a recrawl's `upsertJob` without being clobbered. Tracked rows also carry `appliedAt` (`applicationAppliedAt()` in `lib/application-status.ts`: `submittedAt` → first history entry in `SUBMITTED_APPLICATION_STATUSES` (제출완료 onward) → `updatedAt`; `null` before submission), shared with the Google Sheet sync. The board uses it to mark **recently applied companies** (`lib/company-application-recency.ts`, AI-free, client-side over the tracked list): every other posting of a company (matched by `normalizeCompanyName`) applied to within 1/3/6 calendar months gets a rose/orange/yellow left stripe and a footer line (`N개월 내 지원한 회사 · …`) on its card, a colored dot marker in the panel header, and a notice listing those applications in 공고 상세 — deliberately not a chip, which read like the 신입/경력 badges — applying to several postings of one company in a short window reads as 찔러보기. The posting's own application is excluded; expired/hidden applied postings still count. The same module also marks companies with an application in **작성중** (`indexDraftingCompanyApplications`; open postings only, own posting excluded) in violet: a stripe (only when no recent-application tier applies), a `작성중인 회사` footer line, a header dot and a notice.
- **`sheet_sync_pending`** — retry queue for the Google Sheet sync below (seq only; the payload is rebuilt from current state at send time).
- **`companies`** / **`company_sections`** — company research cache, see below.
- **`application_drafts`** — one cached AI-drafted application per `seq` (see below).
- **`essay_events`** — append-only essay writing/revision log (see "Essay writing log" below).
- **`memos`** — user-written memos, no AI (`lib/memo-types.ts`). `scope='job'` is keyed by `seq` (공고 메모), `scope='company'` by `normalizeCompanyName()` (회사 메모, shared by every posting of that company — the server normalizes from the display name, clients never do). Its own table so a recrawl never clobbers it; a blank memo deletes the row. `GET /api/memos` returns all of them at once (`{job, company}`) because the board shows them on every card; `PUT /api/memos` (`{scope:"job", seq, text}` / `{scope:"company", company, text}`, same-origin, ≤`MEMO_MAX_CHARS`). Edited in 공고 상세 (`components/MemoPanel.tsx`, autosave after typing stops plus a keepalive flush when the posting changes or the page closes), shown as one-line footers on cards, matched by the board search, and included in the 대화로 쓰기 essay-context document as "사용자 메모". Covered by `scripts/tests/memos.cjs`.
- **`ai_usage`** — per-call token/cache usage and cost (`recordAIUsage`), readable via `GET /api/ai-usage?seq=&days=` and shown as one line in the draft panel. (An old `ai_conversations` table may still exist in existing databases; nothing uses it.).
- Experience cards live in `data/experience-cards.json` (JSON file, not a table — see "Vendored external skills" below).

### Company research: `lib/dart.ts` + `lib/company-research.ts`

KOFIA postings carry **no company ID**, only a free-text `company` string, and no financial data at all. `lib/company-normalize.ts`'s `normalizeCompanyName()` (strips `(주)`/`㈜`/`주식회사`/whitespace) is the *only* identity key — always use it, never re-derive normalization elsewhere.

- **`lib/dart.ts`** — OpenDART (전자공시시스템) client, gated on `process.env.DART_API_KEY` (`isDartConfigured()`). There is no company-name search API, so `findCorpCode()` downloads the full corp-code list (`corpCode.xml`, unzipped via the system `unzip` binary — not a new npm dep — and parsed with `cheerio`'s `xmlMode`) once, caches it to `data/dart-corpcodes.json` (refreshed every `DART_CORP_CODE_REFRESH_DAYS`), and matches locally. An exact match compares names with Latin letters spelled out in Hangul on both sides (`hangulizeLatin`), because DART and KOFIA write acronym names differently: DS투자증권 ↔ 디에스투자증권, 케이비자산운용 ↔ KB자산운용. The only fuzzy match allowed is a DART name that contains this name and is at most 4 characters longer (≥60% share). The old reverse rule (DART name contained in this name) tied DS투자증권 and 에픽투자일임 to a one-character corp "자" and 금융투자협회 to "융", and governance then quoted that CEO as disclosed fact. **Research uses DART only for exact matches.** `ensureDartMatch` re-matches anything not stored as exact. `governance_structure` without an exact match still runs, on homepage, postings and press, saying so. `financials` without one returns partial without an AI call. Both sections record `contentJson.dartMatch`. `invalidateFuzzyDartSections()` in `lib/db.ts` runs at startup: for companies still stored as fuzzy, it prefixes governance/financials sections lacking `dartMatch` with `DART_MISMATCH_NOTICE`, marks them partial (so a refresh re-runs them) and clears the match. Every section prompt, including `news`, starts with a **company identity block** (`identityBlock`: homepage/recruiting-mail domains, plus CEO and address from an exact DART match). It tells the model to drop material about same-named companies; small firms' searches had mixed in other companies (케이앤씨인베스트먼트, 한강에셋, 마제스타). Covered by `scripts/tests/dart-match.cjs` and `dart-mismatch-migration.cjs`. `fetchKeyFinancials()` matches accounts by **`account_id` (IFRS code) first, falling back to exact `account_nm` match** — a real bug was found and fixed here: substring-matching account names picked up `자본과부채총계` (assets total) for a `부채총계` (liabilities) search, because `.includes()` matched the wrong row.
- **`lib/company-research.ts`** — five independent sections (`lib/company-section-types.ts`: `overview`, `culture`, `governance_structure`, `financials`, `news`), each with its own TTL (`COMPANY_SECTION_TTL_DAYS` in `lib/config.ts`) so a "refresh" never re-runs sections that are still fresh. All five are deliberately **deep, not quick summaries** — first shipped as a 4-turn `WebSearch`-only Haiku call asking for "3-5문장", which the user correctly called out as too shallow to avoid looking uninformed when applying. The default research model is `claude-sonnet-5-5`, configurable in the settings page, `allowedTools: ["WebSearch", "WebFetch"]` (must actually open and read pages, not just skim search snippets), `maxTurns: 25` for every section including the DART-grounded ones (`financials`/`governance_structure` start from real DART numbers/exec data via `runGroundedResearchSection` but still search+fetch to add industry context and interpretation — a first attempt at `maxTurns: 15` measurably hit the turn ceiling and failed on `governance_structure` in testing, so don't set it lower again without re-verifying live). Prompts explicitly ask for 1000+ characters, multiple paragraphs, ≥3 real sources actually fetched, and — for `overview` — a "why is this company hiring right now" analysis tying the role to the company's current situation. These calls intentionally **bypass `getAIModelOptions()`/FreeRide** and always hit Anthropic directly — WebSearch/WebFetch are native Anthropic server tools a local FreeRide gateway likely can't proxy. Sources are extracted from the model's own `[title](url)` markdown links in its answer, not from parsing tool-call internals. **Page reading:** besides WebSearch/WebFetch, Claude research calls get an in-process MCP tool `read_page` (`lib/research-page-tool.ts`, `mcp__findar__read_page`, server created per call). It exists because WebFetch often failed on Korean company sites. Many have broken certificates (페블즈자산운용 serves the host's `*.gabia.io` cert, 한강에셋 lacks an intermediate), and the model then wrote "원문 미확인" analyses. `read_page` retries over http when https fails on a certificate error and says so in the result. It decodes EUC-KR, follows a frameset first page, strips site chrome and lists same-site links so the model can open 경영공시·회사소개; PDFs are left to WebFetch. It identifies itself (`FindarResearch` UA) and never bypasses bot protection: hosts known to block automated access (thevc.kr AWS WAF, 잡플래닛 Cloudflare, 블라인드, 링크드인) are denied before any request without using budget, and 401/403/429 or challenge pages come back as `[읽기 실패]`. `read_page` and WebFetch share the 5-read budget; `researchToolBudget()` also listens on `PostToolUse`/`PostToolUseFailure` and refunds failed reads (up to 4 per section). `financials` and `governance_structure` also get the code-gathered basics (`basicsBlock(basics, { strict: false })`: homepage text, image text and postings, with no `HOMEPAGE_UNVERIFIED` requirement), plus a prompt line to take 주주·임직원 수 / AUM from the homepage's 경영공시 pages; `news` deliberately does not. Covered by `scripts/tests/research-page-tool.cjs`. **`overview` and `culture` start from code-gathered basics** (`loadCompanyBasics()`, no AI): (1) the company homepage (`lib/company-homepage.ts`), tried in order from the posting's 사이트바로가기 (`getCompanySiteUrls()`), DART 기업개황 `hm_url`, then the recruiter email domain in recent postings (`emailDomainUrls()`, public mail skipped) — 흥국증권 postings have no 사이트바로가기 at all; job-board/ATS and private hosts are skipped, frames/meta-refresh/script redirects are followed (흥국증권's `/` is a frameset to `/index.do`), and up to 4 company subpages (회사개요·사업영역·연혁·CEO·인재상·경영정보…, same site, site chrome stripped, image `alt` sentences read because old sites put the body in images) are read and labeled, EUC-KR decoded, http retry, 10-min cache. When a subpage's content is an image whose `alt` is only a title (한국자산평가 인재상·미션·핵심가치; 흥국증권 사업영역 team list), up to 6 content images from the subpages are downloaded (`contentImages`/`sniffImage`: chrome, decorations, tiny files, images repeated on several subpages and alts that already hold the text are skipped) and `lib/homepage-image-text.ts` transcribes them in one tool-less call with the research model (`inputImages` in `lib/ai-query.ts` → Claude image blocks or Codex `--image`; 1-hour cache), added to the prompt as `<homepage_images>` — the model's WebFetch can't read images either; (2) DART 기업개황 (CEO, address, founding date) only for an **exact** DART match; (3) the company's 4 most recent KOFIA postings with dates and links (`getCompanyRecentJobs()`). The prompt ranks conflicting sources DART·recent postings > homepage > press > job platforms, requires address/CEO/founding date from DART·postings, and says a copyright year is not a freshness signal — a real run called 흥국증권's homepage stale from its "©2008" footer and wrote a wrong 강남 address attributed to the homepage, while one subpage footer still shows an old 종로 address. Homepage pages and DART are listed first in `sources`, and the result records `contentJson.basis` (`{homepage, dart, postings}`). An overview/culture without a basis (made the old way; recognized also by code-attached "DART 기업개황"/"홈페이지 — …" sources) is treated as stale regardless of TTL and may be replaced by a grounded `partial`. `companyResearchNotice()` (returned by `GET /draft`) shows a banner in the essay workspace when the research is missing, old-method, or homepage-unverified — 첨삭 once rejected correct IPO sentences because the cached research was the old wrong one. This exists because the model's own WebFetch once failed on 마스터자산운용's homepage and the overview guessed the business from search results ("국내 주식 롱쇼트" instead of an IPO house) and imported another posting's "책임감 강하고 꼼꼼한 업무태도" line that then reached an essay as this posting's requirement. When the homepage can't be read the model must open it itself or start its answer with `HOMEPAGE_UNVERIFIED` and not assert the business; such a result is saved as `partial`. The research prompt also requires quoted job-posting lines to carry their title and date. Covered by `scripts/tests/company-homepage.cjs`, `company-research.cjs` and `codex-ai.cjs`. Research is **lazy and manual-only** — there is no config flag or background job that researches all KOFIA members automatically; a company is only looked up when its "회사 리서치" tab is opened and the user clicks the refresh button, and only stale/missing sections are (re)run then. A single deep section now realistically takes minutes (real WebFetch calls are slow) and costs meaningfully more than the old shallow version — an accepted, explicit tradeoff for this feature, not true of the rest of the app's AI calls.
- API: `GET /api/companies/[normalizedName]` (pure cache read, no AI cost, upserts the `companies` row from `?displayName=`) and `POST /api/companies/[normalizedName]/research` (SSE, same `data: ...\n\n` framing as the jobs route; body `{displayName, sections?}`).

### Profile & matching: `lib/profile.ts` + `lib/matcher.ts`

- Resume PDFs are **uploaded from the web** (`/profile#resume` → 이력서·포트폴리오, `components/ResumeUploadForm.tsx`) via `GET`/`POST`(multipart `files`)/`DELETE ?name=` `/api/profile/resume`, and stored in `data/resume/` (`lib/resume-files.ts` — `%PDF-` magic check, sanitized basename, 20MB/10 files, same name = replace). `POST /api/profile/resume/analyze` runs `ensureProfile()` immediately instead of waiting for the next crawl. The old repo-root `resume/` dir is legacy: `lib/profile.ts` moves its PDFs into `data/resume/` once at module load and, if content is unchanged, rewrites the cached `sourcesHash` and every job's `matchProfileHash` (`remapMatchProfileHash`) so the move doesn't trigger a re-extraction or full rematch. `ensureProfile()` extracts a structured `Profile` agentically (`allowedTools: ["Read"]`, the SDK reads the PDFs itself) and caches it to `data/profile.json`, keyed by `hashResumeSources()` (file **name + content** hash — re-uploading an identical file costs nothing). Concurrent extractions of the same hash share one in-flight promise. This call **always uses the raw Anthropic API**, never FreeRide, since resumes are PII.
- `Profile.transferableStrengths` (extracted from the resume) feeds the matcher prompt so a CS/dev-heavy resume doesn't implicitly get scored as IT-only fit. A user-written 지원 방향 (`careerGoals`, `data/profile-overrides.json`, `/profile#direction`) used to feed matching, tailoring and review; the user removed it as useless (2026-10-28). Don't re-add it.
- `lib/matcher.ts` has **no category gate** — it already scores every job regardless of category; `positionType`/category bias, if any, comes from the profile's own material, not a code-level restriction.

### Resume tailoring (이력 구성): `lib/resume-tailoring.ts` + `lib/resume-inventory.ts` + `lib/resume-tailoring-contract.ts`

Per-job evaluation of *what to put on the resume*: every resume/applicant-profile item gets a decision — `강조`/`유지`/`축소`/`제외`/`숨김 검토` (plus `판단 보류` for items the model skipped; `normalizeTailoring()` never drops an item). Shown in the job side panel's **이력 구성** tab (`components/ResumeTailoringPanel.tsx`).
- `Profile` is a matching summary and drops small items (old activities, minor certs, hobbies) — exactly the items this feature judges — so `ensureResumeInventory()` separately extracts a **complete item-level list** from the PDFs (`data/resume-inventory.json`, same `hashResumeSources` key, lazy: only on first use, never in the crawl pipeline). `buildApplicantItems()` adds the user-authored `ApplicantProfile` entries (`a.*` ids) deterministically; required form fields (birthdate, gender, contact) are excluded, optional ones (religion, hobbies) included.
- One tool-less Sonnet call per evaluation, direct Anthropic (full resume content = PII). The prompt's honesty rules are the point of the feature: it may recommend *omitting* or *refocusing* but never altering facts, and must warn (`omissionRisk`) instead of recommending omission when leaving an item out could count as 경력 누락/허위 기재.
- `POST /api/applications/[seq]/tailoring` runs as an `ApplicationTask` of kind `"tailoring"` (same task store/polling as essay writing — `ApplicationDraftPanel` filters these out); `GET` is a pure cache read from the `resume_tailoring` table with a `stale` flag (hash of resume files + applicant `updatedAt` + role selection; an empty slot where `careerGoals` used to be is kept so existing evaluations don't all turn stale).

### Application drafting: `lib/essay-revision.ts` + `lib/essay-review.ts` + `lib/application-draft.ts` + `lib/application-method.ts` + `lib/applicant-profile.ts`

- **`lib/applicant-profile.ts`** — a large, 100% user-authored (no AI) structured record: name/English name/gender/birthdate/photo(data URL)/nationality/address/email/phone/disability/veteran/military status, plus repeatable arrays for education, research, language tests, certifications, awards, activities, work experience, and projects. Filled at `/profile#applicant` (`components/ApplicantProfileForm.tsx`) via `GET`/`PUT /api/profile/applicant`, stored in `data/applicant-profile.json`. This exists because the AI-derived `Profile` (from resume PDFs) simply doesn't contain fields like email/birthdate/school name/military service — real Korean application forms (NCS-style especially) ask for all of them, in granular repeated sections. **If you (Claude) are asked to fill out a real application form for the user, `GET /api/profile/applicant` is the authoritative source for this data — use it verbatim, don't re-derive it from the resume.**
- `detectSubmissionMethod()` (`lib/application-method.ts`) is a **pure, AI-free heuristic** run fresh on every draft `GET` (cheap enough not to cache): scans `job.attachments` filenames for an application-template pattern (입사지원서/지원서/...) vs. a consent-form pattern (개인정보...동의서), and `job.rawContent` for a submission email. Real crawled data showed **KOFIA postings are dominated by email+attachment submission**, not web ATS forms — check both signals, don't assume `siteUrl` means a fillable web form.
- **Essays are written in a conversation session, not in the web app.** The user decided (after two rebuilds) to write 자기소개서 directly with Claude in a chat session; the web keeps only saving, hand edits, versions, 첨삭 받기 and 최종본 저장. What was removed and why: the first pipeline (plan → material selection with anchor/coverage gates → write → edit → context/opinion audits → per-step repairs, a resumable "work conversation", three vendored skill texts in every prompt) failed 13 of 20 writing requests and what passed was thin; its replacement (구성 제안 → user-edited outline → 작성 → 문단 다시 쓰기, `essay-writer.ts`/`EssayOutlineEditor`) still fell short of essays written together in a conversation. Do not re-add web-side AI essay writing without the user asking. **Web flow** (`components/ApplicationDraftPanel.tsx` 문항별 자기소개서 + `components/EssayReviewTools.tsx`): (1) **자기소개서 저장** `POST /draft/import` (`importEssay`, no role needed, no AI) stores question + limit + text; same question = new version. (2) Every text change — save, `PUT /draft` hand edit (each question has its own 답변 저장 button next to 최종본으로 저장 and saves only that question; other questions' unsaved edits stay on screen, and 첨삭 받기/최종본 저장/suggestion actions save only their own question first), applied suggestion, version restore — runs `checkEssay()` (`lib/essay-review.ts`, AI-free) and replaces `reviewNotes`: "확인: …" warnings for over-limit, 반말, other-company/school/project names (`forbiddenNames` from `buildEssayContext`), meta/disclaimer phrases, plus `styleReviewNotes`. Applicant numbers are **not** checked against sources (the user's own facts). Warnings never block. (3) **첨삭 받기** `POST /draft/review {question, focus}` (`reviewEssay`, task kind `"revision"`, outcome `"feedback"`, one AI call with a syntax-only JSON retry via `askJson`): compact context from `buildEssayContext()` (posting ≤4k, overview/culture ≤2.5k, credentials, values, edit signals, recent dismissed suggestions from `essay_events`; other-company/school/project names redacted); keeps the rule that the applicant's own facts are never deleted for lacking sources; `validSuggestions()` drops suggestions with unknown numbers, forbidden names or new meta phrases. (4) **최종본으로 저장** `POST /draft/final {question, revision}` (`saveFinalAnswer` → `saveFinalEssay` in `lib/essay-bank.ts`) upserts the current text into `data/essay-bank.json` as a `source: "saved"` entry keyed by `seq`+question (one final per posting/question, re-saving replaces it), with the posting's company and `지원 직무: …` as context — so the user never has to re-upload a finished essay as a file. `GET /draft` returns `finals` for the "최종본 저장됨 / 저장 후 바뀜" badge; `/profile#essays` lists finals (`GET /api/essay-sources` → `finals`) and removes one with `DELETE /api/essay-sources?final=<id>`. Finals feed experience cards (kind `final`) on the next card rebuild; cards are not rebuilt automatically (AI cost). (5) **대화로 쓰기**: a button copies a starter sentence for a Claude chat that tells it to `curl` `GET /api/applications/[seq]/essay-context` (`essayContextDocument()`, AI-free, works before a role is chosen) — one markdown document with the writing guide, posting, overview/culture research (with the stale-research notice), credentials, values, all experience materials (every card the user hasn't excluded, labels redacted too), the user's own edit signals, this posting's saved answers with final-save status, and how to save back (`POST /draft/import` with the current `draft.revision`; CLI requests without an Origin pass `isSameOrigin`). It exists so a chat session reads everything in one call instead of digging through the DB and JSON files. `ESSAY_GUIDE` (shared by 첨삭 and the context document) is kept short and starts with the flow rule — one line of thought, nothing inserted just because it's in the materials, no bridge sentences — which wins over the other lines; it must not contradict the chat session's writing memory (e.g. technical terms stay as they are, length is 97%+ for ≤1,000-char questions). The context document labels research and experience materials as a pool to pick from, not a checklist. More rules made essays worse (format right, flow broken), so prefer removing a rule to adding one. In the chat session, two project skills run after a draft is finished: `.claude/skills/essay-blind-read` (a fresh subagent reads only the answers and points out broken flow and inserted sentences) the vendored, unmodified `.claude/skills/humanizer` (tone only), and `.claude/skills/essay-ai-check` (before submission: many 금융사 screen essays with 무하유 GPT킬러 and drop AI-written ones unread, so `scripts/ai_signals.py` measures the published Korean detector signals locally — comma rates from KatFishNet, sentence-length variance, stock phrases, per paragraph — and the skill checks that every paragraph carries the user's own detail or wording; it never uploads essays to outside detectors or uses evasion tricks like typos or invisible characters). Sources and why jasoseo-plugin/im-not-ai are not used: `skills/vendor/README.md`. Model: the `applicationDraft` setting (label 자기소개서 첨삭). Covered by `scripts/tests/essay-review.cjs` and `application-tasks.cjs`.
- **`lib/essay-bank.ts`** is the "발전 가능한" feedback loop the user asked for: a growing corpus of the user's own past 자소서 writing, stored in `data/essay-bank.json`. Two ways entries get in: (1) the user uploads past 자소서 **and 면접 대본** at `/profile#essays` → 과거 자소서·면접 (`components/EssaySourceUploadForm.tsx`, `GET`/`POST`(multipart `kind`+`files`, or JSON `{kind,title,text}` paste)/`DELETE ?kind=&name=` `/api/essay-sources`). `lib/essay-sources.ts` stores them under `data/essay-sources/{cover-letters,interviews}/` (PDF magic-checked; TXT/MD as-is; DOCX/HWPX converted to `.txt` at upload via system `unzip` — Read can't open them; HWP rejected with a "save as PDF/HWPX" message; the legacy repo-root `cover-letters/` dir is moved in once). `ensureEssayBank()` then extracts **per file**, cached by file name+content hash and model in `bank.files`, so only new/changed files cost a call: PDFs via `allowedTools: ["Read"]`, text inline with no tools; `{company, question, answer, context}` with answers **verbatim** (for text sources `verbatim` is checked in code and the UI warns when it's false); entries carry `kind`/`sourceFile`, and a deleted file's entries are dropped on the next run. A failed file is not retried automatically (writing calls `ensureEssayBank()` every time — that would re-bill on each draft); only "실패한 파일 다시 분석" (`retryFailed`) retries. `styleNotes`/`recurringThemes` come from one tool-less call over the extracted answers, only when the set of analyzed files changes. `POST /api/essay-sources/analyze` runs it in the background; the source-management UI polls `progress`. All bank writes go through `updateBank()` (re-read + atomic rename) because a run takes minutes while edit signals/saved answers keep landing; (2) 최종본 저장 (`saveFinalEssay()`, see above) — these `source: "saved"` entries are never touched by re-extraction. Only the recent edit signals (`summarizeEditPreferences`) go into the review prompt and essay-context document as a style reference. `styleNotes` is still generated but deliberately left out (2026-10-28): it described the old IT 자소서 pattern (수치 결과 → 배운 점 → 직무 연결) and pulled that formula back into new essays; the experiences themselves reach it through experience cards (below). Each saved answer can be added back to the bank, so the corpus is meant to compound over time.
- **`lib/narrative-profile.ts`** (+ `lib/narrative-questions.ts`) fills the gap none of the above cover: the user's actual values, the real reasons behind past choices, and where they want to go — not skills or work history. It exists specifically for jobs whose domain is **distant from the resume's career history**, where `Profile`/`ApplicantProfile`/essay-bank alone push the model toward strained skill-stretching ("data pipeline experience → applicable to risk analysis") instead of a genuine "why this role" narrative. Stored in `data/narrative-profile.json`, same JSON-file convention as `applicant-profile.ts` (no SQLite table), **100% user-authored, no AI extraction** — this data can't be inferred from a resume, and having AI invent it would be exactly the "AI did all the thinking" impression the user is trying to avoid. Two parts: `core` (4 fixed, rarely-changing fields — `coreValues`/`workCriteria`/`futureDirection`/`opennessToNewFields`, the last one being the most direct bridging material, always included in full) and `episodes` (an essay-bank-style growing list, seeded from `NARRATIVE_SEED_QUESTIONS`' 8 reflective questions but extensible via "경험 추가"; each splits `situation` (fact) from `reasoning` (the judgment criteria actually used at the time) so the model can quote `reasoning` as the real motive instead of blending fact and motive). `summarizeNarrativeForPrompt()` ranks episodes by tag/keyword overlap with the job but — this is the key design choice — **never returns an empty result when overlap is zero**; it falls back to the most recent episodes instead, because a zero-overlap job is exactly the "distant job" case where this material is needed most ("looks irrelevant → still include it," not "looks irrelevant → omit it"). No programmatic "is this job distant?" heuristic was added (a keyword-table version was considered and rejected as another brittle layer); instead `buildDraftContext`/`backgroundPromptBlock` in `lib/application-draft.ts` always includes a static instruction telling the model to lean on this material instead of skill-stretching whenever the job looks distant from the resume — the model already has both texts in context and can judge distance itself. Profile UI at `/profile#narrative` (`components/NarrativeProfileForm.tsx`), `GET`/`PUT`/`POST /api/profile/narrative` + `PUT`/`DELETE /api/profile/narrative/[id]`.
- **Stored-answer actions: `lib/essay-revision.ts`.** AI-free operations on saved answers: 자기소개서 저장 (`importEssay`, `POST /draft/import`), apply/dismiss review suggestions (plain string replace), close feedback, restore a version, move a question up/down among this posting's questions (`move`, logged as `answer_moved`; legacy common answers stay in place, and re-saving an existing question via import keeps its position) (`applyEssayAnswerAction`, `POST /draft/answer-action` with the draft `revision` for conflict detection; unknown actions throw), manual edits saved via `PUT /draft` (`recordManualEdit`), and 최종본 저장 (`saveFinalAnswer`). Text-changing operations take an optional `EssayCheck` (routes pass `checkEssay`) that refreshes `reviewNotes`. Every text change appends to `EssayAnswer.versions` (capped at `MAX_ESSAY_VERSIONS`). Manual edits and accepted/dismissed suggestions are logged as `editSignals` in `data/essay-bank.json`; `summarizeEditPreferences()` feeds recent pairs into the review prompt. Old answers may still carry `pendingRevision`/`revisionNeedsInfo` from removed features; they are not shown and only the essay-log backfill reads them.
- **Experience cards (경험 카드): `lib/experience-cards.ts` + `lib/vendor-skills.ts` + `skills/vendor/cover-letter-team/`.** After the essay bank extracts verbatim Q&A, `ensureExperienceCards()` (one tool-less call, `essayBank` model, chained from `POST /api/essay-sources/analyze` or `POST /api/experience-cards`) turns them — plus resume-inventory and 지원 정보 experience items — into cover-letter-team EXP cards (`event_id`, `personal_actions` vs `team_result`, `decision`, …) in `data/experience-cards.json`; `validateCards()` drops cards whose evidence quotes aren't verbatim and items with numbers absent from the quotes. The card schema is the only vendored text still used (`loadVendorSkills().cards`; never edit vendored files, see `skills/vendor/README.md`). Every card goes into the essay context by default; at `/profile#experience` the user only marks cards to leave out (`excluded`, `PATCH /api/experience-cards {id, excluded}`, `getIncludedCards()`). The vendored confirmation gate (`user_confirmed`/`approval`) is not used — the user asked for opt-out instead of opt-in. A rebuild carries exclusions over to cards with the same set of evidence quotes (`carryExclusions`), since ids, event ids and wording change between rebuilds. Excluded cards still contribute their source companies to `forbiddenNames`. Card `origins` (company/role the source was written for) are copied by code; uploads can carry a user-entered company/role (`data/essay-sources/meta.json`, editable later via `PATCH /api/essay-sources`, which rewrites entries and card origins in place without re-analysis). Covered by `scripts/tests/vendor-skills.cjs` and `essay-source-meta.cjs`.
- **Essay writing log (작성 기록): `lib/essay-log.ts` + `lib/essay-log-analysis.ts`.** Every essay action is appended to the SQLite `essay_events` table (append-only — never update or delete rows): 자기소개서 저장(`answer_imported`), 직접 수정, 첨삭 받기 요청→피드백→제안별 반영/넘김→닫기(손대지 않은 제안 포함), 버전 복원, 최종본 저장(`saved_to_bank`). Rows from removed features (작성 요청/초안, 고쳐쓰기, 구성 제안) stay readable. `application_drafts` only holds current state (closed feedback and discarded rewrites vanish there), so this log is the only record of *how* an answer evolved and what the user asked for or rejected. Events carry `actor` (user/ai/system), a `threadId` linking a request to its AI result and the user's accept/discard (stored as `threadId` on `PendingRevision`/`EssayFeedback`/`RevisionNeedsInfo`), full `textBefore`/`textAfter`, and a deterministic `analysis` (`analyzeEssayChange`: sentence-level hunks split per paragraph, each with `zone` 도입/본문/마무리, paragraph number, and tags like 단서 제거/의견형→단정형/축약/문장 분리, plus `inspectEssayStyle` codes resolved/introduced). `summarizeEssayEvents` aggregates requests with outcomes, suggestion stats per category, where/how the user edits by hand, and which style issues the user fixes vs. the AI introduces. Read via `GET /api/essay-log` (`view=summary`, `format=jsonl` export, filters `seq`/`question`/`type`/`threadId`/`since`/`until`/`limit`/`text=0`). No AI calls; logging failures are swallowed so they never block the actual save. On first load it backfills answers that have no events yet from their `versions` and any open feedback/rewrite (marked `detail.backfilled`). Failures carry the reason. **Any new essay action must log an event here.** Covered by `scripts/tests/essay-log.cjs`.
- **Essay style rules: `lib/essay-style.ts`.** `STYLE_RULES` documents problems seen in real output (the review prompt uses the shorter `ESSAY_GUIDE` in `lib/essay-review.ts`): personal experiences grafted one line per claim instead of one coherent paragraph, experiences stretched into analogies for company/industry problems, self-descriptions contradicting the story told, research facts piled in (including ones the essay itself calls "just a reference"), "한 증권사"-style anonymized sources, hedges ("다만") and opinion endings ("생각합니다/봅니다") on every sentence, vague metaphors. `META_SOURCE`/`DISCLAIMER` catch phrases that cite the posting or research in the body ("공고상", "협회에 게시된", "조사한 바에 따르면", "~로 알고 있습니다", "짐작합니다") or excuse a weak link ("실무와는 다르지만", "접점이 있다고 생각합니다") — all taken from drafts the user rejected. They are reported, not blocking: `checkEssay()`/`essayWarnings()` add a "확인:" note on every save, and 첨삭 받기 drops suggestions that add one. `lintEssayStyle()`/`styleReviewNotes()` are free deterministic checks (hedge count, opinion-ending ratio, same final word 3× in a row, anonymized-source phrases, sentences >110 chars) appended to `reviewNotes` as "문체 점검: …" and fed into the review prompt. Covered by `scripts/tests/essay-style.cjs`.
- **No Playwright / in-app browser automation.** It was prototyped and removed: real ATS forms (tested live against a greetinghr-hosted form) vary too much site-to-site — inconsistent labels, deeply nested field names, file uploads, consent checkboxes — for a hardcoded field-matcher to be reliable. Instead, `ApplicationDraftPanel` surfaces a copyable prompt (`이 공고 지원 도와줘 (seq=N)`) for the user to hand to a live Claude Code + Claude-in-Chrome session, which reads the real page and fills it with judgment — pulling personal info from `GET /api/profile/applicant` and essay content from the job's draft. Findar's job stops at producing a good draft + submission-method hint; it never automates the actual site, and never has code capable of clicking a submit button.

### Company job-site watch: `lib/company-watch.ts` + `lib/company-watchlist.ts` + `lib/watch-adapters.ts` + `lib/job-dedup.ts`

Design: `docs/multi-source-jobs.md`. KOFIA postings often lack 신입 공채·인턴 that firms post only on their own ATS. After the KOFIA step, `GET /api/jobs` (`?watch=off|force`, default daily) walks the watchlist (`data/company-watchlist.json`, default `DEFAULT_WATCHLIST`; edited at `/settings` → 수집 범위 via `GET`/`PATCH /api/watchlist`). Adapters: `greeting`, `saraminAts`, and `recruiterAppsite` (old recruiter.co.kr: robots.txt allows only `/appsite/`, so it stores list fields — title, 구분, 접수 기간 — as the body and never opens `/app/jobnotice/view`), and `pageWatch` (company job boards in server HTML: post links = same-site links with a new numeric ID, title from the row, rows marked 마감/past/older-year skipped, at most 5 new posts per board per day; per-site `jsLinkTemplate` for `javascript:fn('92')` links and `itemSelector` for link-less lists; a post whose summary has no positions and whose title has no hiring word is recorded in `watch_not_postings` and never reopened); `endpoint` (a site's own list/detail API, configured per company as `api` field paths: GET or form POST list, ISO or `YYYY.MM.DD` dates, JSON or HTML detail — IBK, 신한투자증권, applyin sites 하나대체투자·부국증권; requests send `Accept: application/json` because applyin serves HTML or JSON on the same URL; 한투 채용포탈 encrypts its request parameters in the browser and is treated as blocked), and `workday` (foreign firms: `POST /wday/cxs/{tenant}/{site}/jobs` with `searchText: "Seoul"`, Korea-located postings only, deadline/start date from the detail JSON — Morgan Stanley, Deutsche Bank, Barings, BlackRock), and `tossCareer` (토스증권 from the Toss affiliates' shared Greenhouse-format feed `api-public.toss.im/…/career/job-groups`, ~6MB with descriptions inline, filtered by the 자회사 metadata). Toss and Workday list only current openings, so the "open over 180 days without a deadline" filter doesn't apply to them; titles that are application-form entries ("입사지원서 작성") are skipped. Not collected on purpose: samsungcareers (list API needs a browser session) and CareerLink (list comes from a separate host, api.inhr.co.kr). Other source types are link-only. `lib/watch-fetch.ts` checks robots.txt (longest match), uses the FindarResearch UA, 1s per host, and never bypasses blocks (`blocked` status, retried after 7 days). Source is encoded in the seq (`lib/job-source.ts`: numeric = KOFIA, `manual-`, `greeting-<id>`, `saraminats-<slug>-<id>`, `recruiter-<slug>-<jobnoticeSn>`, `page-<url hash>`, `api-<slug>-<id>`, `workday-<tenant>-<reqId>`, `toss-<id>`); `postingLink()` lives there. Duplicates (AI-free: posting URL with an ID, else title Dice ≥0.7 — or one title key containing the other — with deadline ±1 / Dice ≥0.85 without) go to `job_links` and are excluded from `getActiveJobs()`; KOFIA postings arriving later are linked by `linkKofiaDuplicates()` (user-touched or manual side kept). A wrong merge is undone from 공고 상세 (`components/JobLinksNotice.tsx`, `GET`/`POST /api/jobs/links`): the `job_links` row is kept with `separatedAt` so the pair is never re-linked, and an unstored ATS posting is fetched on the next refresh. Thin bodies (<300 chars besides the title) are filled by `lib/watch-content.ts`: first text from non-form PDF/DOCX/HWPX attachments (no AI; 입사지원서·동의서 names skipped, type sniffed from bytes, HWP unreadable), then, if still thin, body images transcribed with the `postingImage` model (`transcribePostingImages`, once per posting, ≤6 images, sides ≤8000px). Attachment names also go into `attachments` for `detectSubmissionMethod`. Postings that vanish from an ATS list get `jobs.sourceClosedAt` (not in the upsert SET). Runs are recorded in `watch_runs`. Covered by `scripts/tests/company-watch.cjs`.

### Hiring-season alerts: `lib/hiring-season.ts`

Companies whose 신입 공채 can't be collected (recruiter.co.kr 신형, 나인하이어, 한화인, robots.txt, encrypted requests) still get press coverage. Covered by `scripts/tests/hiring-season.cjs`.

When `POST /api/applications` changes a status, `after()` pushes that application to the user's own 지원 현황 Google Sheet via an Apps Script web app (`scripts/google-sheet-sync.gs`, pasted into the sheet's Apps Script editor and deployed by the user — not an MCP connector, which the app itself can't call). Gated on `FINDAR_SHEET_SYNC_URL` + `FINDAR_SHEET_SYNC_TOKEN`; no-op without them. Only statuses from `제출완료` onward are written (검토중/작성중 are "not applied yet"). The script matches rows by the KOFIA `seq=` in the 링크 column, updates only 단계/결과 on existing rows (other cells only if blank, so manual edits survive), leaves 이력서 버전 blank, and colors 결과 (탈락 `#ff6d01`, 합격 `#4285f4`). Sends are serialized in-process so rapid status changes can't land out of order; failures stay in `sheet_sync_pending` and are retried on the next status change or `GET /api/applications/tracked`.

### Env vars

None are committed (`.env*` is gitignored). Relevant ones: `DART_API_KEY` (OpenDART; company research degrades gracefully without it — company-research sections just report "DART 연동이 설정되지 않았습니다", nothing crashes), `FINDAR_SHEET_SYNC_URL`/`FINDAR_SHEET_SYNC_TOKEN` (Google Sheet sync, optional), `USE_FREERIDE`/`FREERIDE_BASE_URL`/`FREERIDE_MODEL` (see FreeRide note above; standard Anthropic auth env vars are consumed inside the SDK and never referenced by name in app code).

## Conventions specific to this repo

- **Korean UI strings stay in Korean** (titles, badges, status messages, filter labels, prompts).
- Category classification (`lib/position-categories.ts`) has **no fixed whitelist in the AI prompt** — `CATEGORY_RULES` is a client+server-shared keyword-matching table, order-sensitive (first match wins, so more specific categories like 퀀트/WM-PB must precede broad ones like IT/개발). AI-returned `positions` are always free text; categorization happens afterward in code.
- Failure mode for summarization/matching/company-research/drafting is **degraded entries**, never dropped/thrown data: `positionType: "미분류"`/`jdSummary: "요약 실패"` for jobs, `FALLBACK_MATCH` for matches, `status: "failed"|"partial"` rows (with an explanatory `content` string) for company sections — preserve this pattern in any new AI call.
- New mutable per-job user state needs to survive a recrawl's `upsertJob()` without being clobbered. Two ways to do that: its own table (`applications`, `application_drafts`), or a `jobs` column deliberately left OUT of `upsertJobStmt`'s `ON CONFLICT DO UPDATE SET` clause (`hidden`, `bookmarked`) — either is fine, but a new `jobs` column that *is* included in that SET clause will silently reset on every recrawl.
- AI calls that only see *derived* data (summaries, profile fields, public company info) may route through `getAIModelOptions()`/FreeRide, matching `matcher.ts`'s existing precedent; calls touching raw resume PDFs (`lib/profile.ts`) or web research (`lib/company-research.ts`) use the shared `lib/ai-query.ts` provider dispatcher. FreeRide remains limited to public-job summary/matching; raw documents are never sent to FreeRide.
- Never add code capable of submitting a third-party form or clicking a submit-like control — the whole application-assist feature set is designed to stop one step before that, by construction, not just by prompt instruction.

### AI 작업 취소

`ApplicationTaskCancelButton` sends same-origin `DELETE /api/applications/[seq]/tasks?id=...`. Server-owned controllers distinguish queued cancellation from running cleanup (`cancelling` → `cancelled`); UI navigation/disconnect still does not cancel work. `lib/ai-operation.ts` scopes a signal across nested AI calls, and `lib/ai-query.ts` forwards it to Claude and Codex. Guards prevent late output from overwriting drafts, revisions, research, tailoring, or document downloads. Shared essay-source/inventory extraction keeps running while another consumer still needs it, and aborts when its last consumer cancels. Task cancellation requests are recorded as `task_cancel_requested` in essay history.
